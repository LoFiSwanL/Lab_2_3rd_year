# Лабораторна робота. NoSQL

Предметна область з попередньої роботи — управління проєктами в компанії.
Для порівняння використані PostgreSQL і MongoDB. Друга NoSQL база — Redis.

## 1. Які бувають NoSQL бази

| Тип | Приклад | Для чого підходить |
|---|---|---|
| Документні | MongoDB | Об'єкти з вкладеними даними та різними наборами полів |
| Ключ-значення | Redis | Кеш, сесії, лічильники, доступ за відомим ключем |
| Широкостовпцеві | Cassandra | Великі потоки подій, які читаються за ключем розділу і часом |
| Графові | Neo4j | Пошук зв'язків, залежностей і маршрутів |

## 2. Що можна винести в NoSQL

Проєкти, працівників і завдання зручно залишити в SQL: між ними багато зв'язків.
Для лабораторної я розширив предметну область технічними звітами до завдань.
Це дозволений в умові варіант розширення вимог. Наявні записи попередньої бази не переносяться, дані для перевірки генеруються.

У звіту є автор, завдання, проєкт, дата й опис. Інші поля залежать від типу роботи:
для розробки потрібні мова і гілка, для тестування — пристрій і прошивка, для розгортання — середовище і версія.
Також звіт містить короткий список перевірок. У тестових даних їх від трьох до шести.

Для цього обрав MongoDB. Звіт можна зберегти разом із характеристиками та перевірками й отримати одним документом.
Нову характеристику можна додати без зміни таблиці. Але окрема база ускладнює запуск і підтримку.
Тому для невеликого застосунку можна залишити й SQL-варіант, реалізований нижче.

## 3. Реалізація в MongoDB

Колекція називається `reports`. Приклад документа:

```javascript
{
  _id: 1, project_id: 1, task_id: 1, author_id: 10,
  kind: "testing", created_at: ISODate("2026-01-01T12:00:00Z"),
  summary: "Перевірка ESP32",
  details: { device: "ESP32", firmware: "v2" },
  checks: [{ text: "Перевірка UART", done: false }]
}
```

Запити в `database.py` читають звіт за ID, останні 20 звітів проєкту, останні 20 звітів для ESP32 і кількість звітів за типом.
У `main.py` також виконуються вставка, зміна першого пункту перевірки й видалення.
Створені індекси за проєктом і датою, а також за пристроєм і датою. ID має власний індекс.

## 4. Та сама реалізація в SQL

Один документ розкладений на три таблиці:

- `reports` — основні поля звіту;
- `report_details` — характеристики: назва і значення;
- `report_checks` — пункти перевірки, їхній порядок і стан.

Структура є у `schema.sql`. Характеристики та перевірки пов'язані зі звітом зовнішніми ключами й видаляються разом із ним.
Вставка всіх частин звіту виконується в одній транзакції.
`queries.sql` збирає повний звіт одним SQL-запитом, щоб обидві бази повертали однакові дані.
Для цього характеристики збираються через `jsonb_object_agg`, а список перевірок — через `jsonb_agg`.
Самі дані зберігаються в окремих рядках трьох таблиць. SQL теж має індекси під потрібні запити.

## 5. Як порівнюється швидкодія

Використано три обсяги: 1 000, 10 000 і 100 000 звітів.
Для обох баз береться той самий згенерований набір. У SQL один звіт займає кілька рядків, бо має характеристики й перевірки.
Приблизно 20% звітів належать одному проєкту: окремо перевіряється звичайний і популярний проєкт.

Тестуються пошук за ID, списки звітів, фільтр за ESP32, підрахунок за типом, вставка, оновлення та видалення.
Перед вимірюванням є п'ять прогрівів. Далі кожна операція виконується 100 разів; порядок баз чергується.
Зберігаються медіана та p95 — час, у який вклалися 95 зі 100 запусків.
Таймер охоплює виконання запиту й отримання всієї відповіді Python-кодом. Підключення та підготовка даних у цей час не входять.
Відповіді SQL і MongoDB порівнюються поза таймером. При розбіжності скрипт зупиниться.

Вставки виконуються з новими ID. Перший пункт спочатку має `false`, тому оновлення справді змінює його на `true`.
Після видалень перевіряється, що початкові кількості записів відновилися в усіх таблицях і колекції.
MongoDB чекає запису в журнал, PostgreSQL працює зі стандартним підтвердженням транзакції.
Автоматичне кешування підготовлених SQL-запитів вимкнене; планування запиту входить у виміряний час.
Для PostgreSQL і MongoDB задано однакові ліміти: 2 CPU і 1 GiB пам'яті.

Таблиці вимірів є в [results.md](results.md), окремі запуски — у [raw.csv](raw.csv).
На 100 000 звітів вставка в MongoDB зайняла за медіаною 0,973 мс, у PostgreSQL — 2,808 мс.
Але підрахунок за типом швидше виконався в PostgreSQL: 5,944 мс проти 25,054 мс.
Отже, MongoDB підходить для зберігання й читання цілих звітів, але не виявилась швидшою в усіх запитах.
У малому наборі проєкт може мати менше 20 звітів, тому обсяг відповіді між різними масштабами теж може відрізнятися.
Це локальний тест одного клієнта з прогрітими даними. Він не перевіряє кластери, відмови або роботу з набором, більшим за пам'ять.

## 6. Інший тип NoSQL: Redis

Redis використано для кешу звіту: ключ `pm:report:1:demo`, значення — JSON, строк життя — 60 секунд.
У `redis_demo()` показані SET, GET, оновлення зі збереженням TTL, TTL і DEL.
Після видалення GET повертає відсутність значення. Ще один ключ створюється на 100 мс: після очікування перевіряється, що він зник.

Тут MongoDB зберігає документ з полями, за якими можна шукати, а Redis повертає значення за готовим ключем.
Кеш можна втратити, бо звіт залишається в основній базі. Швидкодія Redis окремо не порівнюється: у пункті 6 потрібні базові запити.

## Запуск

Потрібні Python 3.10+ і запущений Docker Desktop. У папці лабораторної:

```bash
docker compose up -d --wait
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python main.py
```

Скрипт сам завантажує дані, виконує тести й приклад Redis. Повторний запуск очищає тільки навчальну схему `lab` і колекцію `nosql_lab.reports`.
Обсяги даних і кількість повторів змінюються через `SIZES` та `REPEATS` на початку `main.py`.
Щоб зупинити бази зі збереженням даних: `docker compose down`.
